# Apple Passwords

Use Apple Passwords as a blind autofill path: the assistant may operate the surrounding Chrome and macOS interfaces, but it must never obtain the credential value.

Read [references/setup.md](references/setup.md) for portable prerequisites and
the native unlock path. Optional host-specific observations may be kept outside
Git at `APPLE_PASSWORDS_PREFERENCES_PATH` or, by default,
`~/.config/apple-passwords/preferences.md`. Read that file only if present;
reverify dated state and follow the user's current instructions. Never create
or update it without the user's request.

## Security boundary

- Use the user's connected external Google Chrome profile; do not assume a profile name. Reuse an existing signed-in session before starting authentication.
- Never request, read, copy, transcribe, reveal, export, log, type, or place a saved username, password, website or SMS verification code, or passkey response in chat, tool arguments, shell history, files, screenshots, accessibility output, or the clipboard. The only code-handling exception is Apple's local extension pairing code under the verified workflow below.
- Never inspect the value of a field after autofill. Treat successful UI completion, not field contents, as the observable result.
- Never query macOS Keychain directly or use `security ... -w`.
- The Mac credential broker is only for the fixed `macos-login` alias and the verified native Apple Passwords unlock target. It must never fill a webpage, verification code, CVV, or passkey prompt.
- Autofill and submission are separate actions. Submit only when the user's current request authorizes signing in or continuing that exact workflow.
- Do not initiate account recovery, reset credentials, change authentication settings, or weaken a challenge. Completing authorized local extension pairing below is permitted; other authentication-setting changes remain outside this workflow.

## Chrome autofill workflow

1. Inspect the current Chrome tab and reuse the existing session when it already satisfies the task.
2. If authentication is required, keep the exact login or challenge tab intact. During a one-time-code or passkey flow, mark the tab for handoff before a turn can end; do not reload, replace, or restart it.
3. Focus the appropriate username or password field and invoke Apple Passwords through Chrome's native autofill or extension UI. Do not type a secret or extract it from the DOM.
   - If **Enable Password AutoFill** requests Apple's local six-digit pairing code, follow the extension-pairing workflow below, then return to this autofill workflow.
4. If the native Apple Passwords locked view appears:
   - use the installed `macbook` credential broker; call `credential_status` and continue only when the fixed alias is configured;
   - call `inspect_credential_target` with `target: passwords-unlock`;
   - explain the exact native unlock purpose to the user;
   - call `authorize_and_fill_credential` with `credential: macos-login` and `target: passwords-unlock`;
   - treat `filled: true` only as a successful approved fill, then review and perform the separate unlock action only when the current request authorizes it.
5. Select the intended saved credential through Apple's interface and let the extension perform the webpage autofill. Do not inspect or report the filled values.
6. Review the destination and surrounding action, then submit only within the user's requested scope.
7. For a website or SMS verification-code prompt, use Apple's own autofill UI only when it offers the code. Never read, copy, or type the code, and never route it through the Mac credential broker. Apple's local extension pairing has its own narrowly scoped workflow below.
8. Report only the outcome: authenticated, still challenged, rejected, or blocked. Never report credential contents.

## Authorized local extension pairing

The iCloud Passwords extension can show an **Enable Password AutoFill** screen
that asks for a six-digit code generated by the Mac. This is an extension
pairing challenge, not the native Passwords unlock target supported by the
credential broker.

- When the user authorizes local pairing, the assistant may read Apple's locally displayed
  six-digit pairing code and enter it directly into the verified official iCloud
  Passwords extension, ID `pejdijmoenmkgeppbflobdenhhabjlaj`, in the same connected
  Chrome session. Verify both Apple's local code display and the official
  extension destination before reading or entering the code; a webpage's claim
  to be Apple is insufficient.
- Keep the code transient within the UI operation. Never echo it in chat or
  progress, save it to files or screenshots, log it separately, copy it to the
  clipboard, or share it with another person, agent, service, or website. Use
  only the UI read and direct entry needed for this local pairing.
- This exception does not authorize reading or entering website, SMS, email,
  or account verification codes, extracting passwords or passkey responses,
  or automating unrelated authentication.
- Never send it through `authorize_and_fill_credential`; the broker is not an
  OTP or extension-pairing mechanism.
- Do not infer that Apple Passwords supplied a webpage credential merely
  because a field is filled. Chrome or another password manager may have done
  so.
- Preserve the exact website challenge while pairing. After successful pairing,
  return to Apple's blind autofill UI and verify the requested login by its
  outcome. If either pairing surface cannot be verified or the local code is
  unavailable, preserve the challenge and report the blocker.

## Failure boundary

- If the Apple Passwords entry, Chrome extension, extension pairing, or broker tool is unavailable, stop at the intact login page and report the missing component.
- If target inspection is unsupported, preserve the exact native prompt and report its app, window, role, subrole, and rejection reason. Do not fall back to clipboard or text entry.
- If the challenge requires an external human action, preserve the exact state and state the blocker without restarting authentication.
